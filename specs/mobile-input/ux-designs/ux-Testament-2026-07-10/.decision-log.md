## Technical constraints established from the codebase (not assumptions)

1. **`MOVE` is 8-directional.** `MovePayload = { dx: number; dy: number; walk?: boolean }`
   with `dx`/`dy` as integers in `{-1,0,1}` (`Vector2i` on the client). A joystick's
   angle therefore **quantizes to 8 directions** — the same precision the keyboard
   has. Analog direction would require a server change (`stepPlayer`) and is out of scope.
2. **`walk` already exists on the wire.** The client asks to walk; the **server**
   applies `WALK_SPEED` (I1). A joystick's *magnitude* can drive this flag with
   **zero server change**.
3. **Implemented client→server intents:** `MOVE`, `PROBE`, `EXTRACT` (+ lobby msgs).
   **There is no `ATTACK` intent.**
4. **Attack is designed canon but unimplemented.** `docs/systems/combat.md`: melee
   core (light/heavy, stagger, parry — "Future Expansion"), dodge/ward gated on
   reading the **Omen** sign. So the action zone must be *reserved and grammared*,
   not populated with buttons the server would reject.
5. **Station interaction is proximity-gated and already contextual.** `_active_station`
   drives a bottom-centre "Press E — <Station>" prompt. It is a *render hint*; the
   server independently enforces `NOT_AT_*`.
6. **Affordance ≠ authority** (P62 heritage). Showing/hiding a control never
   authorizes; a raced `NOT_AT_*` / `PARTY_NOT_READY` / kit-gate error must still surface.

## Constraints that shape the design

- **Min tap target ≈ 40 logical px.** At 640×360 logical, a 2340×1080 landscape phone
  resolves to integer factor 3 (logical 780×360). A 48dp target on a ~400dpi phone is
  ~120 physical px ÷ 3 = **~40 logical px** — 6% of logical width, 11% of height.
  Everything finger-operable must clear this. *(Derived; verify on device.)*
- **No hover on touch.** The notice board currently uses **hover-raise** to bring a
  notice to front (T134). Touch has no hover state — this interaction must be redesigned.
- **Thumb occlusion.** Both bottom corners are covered by thumbs in landscape grip.
  Critical readouts must not live there. The status line currently does.
- **Multitouch is mandatory.** Joystick + action pressed simultaneously requires raw
  `InputEventScreenTouch`/`ScreenDrag` tracked **by finger `index`**. Godot's
  `emulate_mouse_from_touch` is single-pointer and cannot express this; it must stay on
  for popup `Button`s but must not own the field HUD.
- **Safe area / notches.** `DisplayServer.get_display_safe_area()` insets required.
- **Portrait is unverified** (TD-042); orientation policy is an open question.

## Validation of the developer's proposal

**Endorsed — the floating joystick.** A joystick that materialises where the thumb
lands, and is invisible until then, is the correct pattern. It is the standard
"non-invasive" solution and it beats a fixed stick (no reaching, no drift-off).

**Amended — "a specified radius."** A control the player must *find* is not
discoverable. Change the mental model from **target** to **zone**: the whole left
region is live, and the stick spawns under whatever thumb touches it. Same
non-invasiveness; nothing to hunt for.

**Rejected — action buttons that only appear on touch.** An action button revealed by
touching where it would be is unusable: the player cannot know where to press, and the
press that reveals it also fires it. It inverts cause and effect.

**Counter-proposal — actions appear when they are _legal_, not when the screen is
touched.** Testament already works this way: the "Press E" prompt exists only when a
station is in range. Bind the action cluster to *game state* (station in range → Interact;
kit carries a stimulus → Probe; standing on the extraction tile → Extract). The screen is
empty while nothing is actionable — the developer's actual goal — without the
discoverability trap. Combat verbs join the cluster when the server accepts them.

**Open:** whether the joystick's magnitude drives walk/run; how the board is operated
without hover; orientation policy; stakes.

## Decisions (developer, 2026-07-10)

**D1 — Action cluster is contextual: a control exists only while its action is legal.**
Station in range → Interact; bag carries a stimulus → Probe; on the extraction tile →
Extract. Mirrors the existing proximity prompt, so desktop and touch share one
affordance model. *Rejected:* touch-reveal (the revealing press is also the activating
press) and a persistent dimmed cluster (permanent furniture on a 640×360 viewport).

**D2 — Movement is a floating stick inside a left-hand zone.** The zone is invisible;
the stick spawns centred under the thumb on touch-down, steers on drag, dismisses on
release. *Rejected:* a fixed stick (thumb drift, hostile to grip variation) and
tap-to-move (collides with the Omen dodge window in `combat.md`).

**D3 — Stick magnitude drives the existing `walk` flag.** Inner ring → `walk:true`;
outer ring → `walk:false` (run). Angle quantizes to the 8 directions `MOVE` accepts.
**Zero server change** — the client asks, the server applies `WALK_SPEED` (I1).
*Rejected:* always-run (mobile would lose the quiet register, which feeds field
pressure) and a sticky walk toggle (spends a scarce action slot on a modifier).

**D4 — A tap on a live notice opens the full-screen reader directly.** No hover, no
intermediate selection. The reader also resolves the ~40px tap-target floor: tiny
scattered notices are never read in place. Overlap resolves by draw order (topmost
wins). *Rejected:* two-stage select→open (a tap tax on every open) and long-press peek
(undiscoverable; conflicts with any future board pan).

## Decisions after the Reviewer Gate (developer, 2026-07-10)

**D5 — Probe is a radial wheel on one stable slot (resolves C2).** Press the Probe button
(touch-**down**, *no hold timer*) → a wheel blooms centred on the thumb, one wedge per
**carried** stimulus; drag highlights a wedge and previews its caption; **release commits**
`PROBE { stimulus }`. `STIMULI` is exactly four (`FLAME`/`COLD`/`SALT`/`LIGHT`,
`signs.ts:27`), so the wheel is four cardinal wedges — the same directional vocabulary the
stick speaks. One gesture grammar for both thumbs.
- **Fixed angle per stimulus** (FLAME up, COLD right, SALT down, LIGHT left) regardless of
  bag contents, so directional memory survives requisition. An uncarried stimulus has **no
  wedge** (consistent with "unavailable means absent, never greyed").
- **This is not the two-stage tap rejected for the board (D4).** That was two discrete
  commits with a persistent selection between them. This is one continuous gesture with a
  live preview and a single commit on release.
- **The wheel belongs to Probe alone.** `ATTACK`/`DODGE` are instant-press; a future
  implementer must not wheel the dodge.

**D6 — Releasing in the wheel's centre cancels.** Nothing is sent. Probing costs exposure
(`room.exposure += PROBE_EXPOSURE_COST`, `probe.ts:41`), so an exposure-spending action gets
a free abort: press, look, slide back, let go. A bare tap therefore sends nothing — safe by
default. *Rejected:* commit-last-used on centre (the timid gesture would silently spend
exposure, and there would be no abort).

**D7 — Press-drag-release only; no sticky mode.** One interaction, no settings surface.
> **Logged trade (accessibility H9 remains OPEN).** The wheel and the stick both require a
> sustained press-and-drag. Players with tremor, limited grip endurance, or one usable hand
> are not accommodated, and a slipped thumb on the wheel costs exposure. This is a *conscious
> exclusion*, not an oversight. Revisit if mobile ships to a wide audience; the standard
> remedy (a latching "sticky" wheel: tap to open, tap a wedge, tap centre to cancel) is
> designed and costed, and can be added without changing the wire.

**D8 — All four validation blockers accepted:**
- **C1** → build the boot self-check **for real**, as a first deliverable. Stop calling it
  precedent; the repo has never run one. `quantize8`/`next_walk` are pure `static func`s.
- **H1** → record now: `ATTACK`/`DODGE`, when populated, are gated on the Seeker's
  **capability** (kit/perception), **never** on the live state of any Incarnate sign. A dodge
  control's presence must be identical whether or not an Omen is firing.
- **H6** → tap targets derive at runtime from `DisplayServer.screen_get_dpi()`; 40 logical px
  is a lower bound, not the target. The HUD is the declared non-diegetic surface, so it need
  not be grid-locked — the world stays on the integer grid.
- **H7/H8** → refusal becomes a **luminance** event; the walk/run register becomes a **shape**
  difference. Both stay inside the locked Ash & Ember palette.
